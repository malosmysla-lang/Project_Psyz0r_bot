# Реестр матчей: сбор, публикация и границы выводов

Сборщик `server/telemetry/psyz_match_collector.py` — отдельный read-only ZMQ SUB-процесс. Подключается только к 127.0.0.1:27961; не отправляет команды в игру, не меняет AI, не использует отсутствующий damage-hook и не требует перезапуска QL. Схема событий сверена с исходником [minqlx StatsListener](https://github.com/MinoMino/minqlx/blob/master/python/minqlx/_zmq.py) и [моделью QL stats](https://github.com/quakelive-server-standards/ql-stats-model).

На сервере user-unit `psyz-match-collector.service` запускается от qlserver. Для сохранения процесса после выхода SSH включён user linger. QL-сервисы и их PID этим не меняются. Остановка сборщика: `systemctl --user stop psyz-match-collector.service`; отключение автозапуска: `systemctl --user disable psyz-match-collector.service`.

## Что записывается

- MATCH_STARTED фиксирует версию из активного cfg и SHA native-библиотеки, карту и время получения события.
- PLAYER_STATS с WARMUP=false даёт счёт, damage, оружейные S/H/DG/K и PICKUPS. Два бота со STEAM_ID=0 не сливаются: внутренний ключ дополнен именем. Steam ID не публикуются.
- MATCH_REPORT завершает запись. Сборщик ждёт 4с после последнего события, чтобы принять поздние PLAYER_STATS. Неполная пара не выдаётся за полноценную дуэль.
- Ретрансляции дедуплицируются по MATCH_GUID; исправленные данные обновляют ту же запись. Файл заменяется атомарно. Перезапуск восстанавливает буфер.
- `private_state.json` хранит служебное состояние с правами 600; на сайт он не копируется. Публикуется только `public_matches.json` с ограниченными полями.

У серверных оружейных счётчиков accuracy рассчитывается как H/S, только если S>0 и 0≤H≤S. Нет выстрелов или неоднозначная семантика — null. Демо может содержать непосредственно заявленную accuracy; источник хранится отдельно. Splash и дробь нельзя считать эквивалентными hitscan.

## Как обновляется сайт

`tools/sync_match_ledger.py` на этом Windows-ПК каждые 20с забирает только public_matches.json через существующий SSH. Выделенный Git worktree под out используется только для `docs/training/MATCH_LEDGER.json`. Перед switch проверяется корень worktree; force-push и команды серверного управления отсутствуют. При изменении матчей создаётся отдельный data-коммит в main. При конфликте push отклоняется и следующая итерация повторяет merge по ID.

Сайт и переносимый HTML при доступном интернете каждые 30с читают этот открытый JSON с GitHub. Офлайн остаётся встроенный снимок. Есть задержка завершения/публикации/CDN: это не кадровая телеметрия. Синхронизация зависит от включённого ПК и работающего watcher; после перезагрузки watcher нужно запустить снова. Сам серверный сборщик работает независимо от ПК и сохраняет матчи до следующей синхронизации.

Запуск вручную: `python tools/sync_match_ledger.py`. Разовая проверка без push: `python tools/sync_match_ledger.py --once --dry-run`. Служебные PID/логи — out/live-ledger. Нельзя публиковать private_state, cfg, пароли ZMQ или сырые runtime-логи.

## Историческая база и «учится ли бот»

Начальный реестр: 7 известных матчей Psyz0r и 59 записей базового Xaero из доступных демо/серверного прогона. Старые версии, не сохранённые вместе с записью, отмечены unknown. У архивного Xaero skill не восстанавливается по имени. Пятиминутный прогон 0.7.9 содержит 4:9 и подборы; оружейная точность и damage там неизвестны и не заменяются нулями.

Автоматического обучения модели сейчас нет. Меняются вручную версии правил; сборщик только собирает данные. Индикатор сравнимости группирует одну версию/native SHA, карту, тип/имя соперника и матчи не короче 5 минут. До 10 сопоставимых матчей вывод — «недостаточно данных»; после можно считать описательные изменения, но не объявлять доказанное обучение или причинность. Прерванные игры исключаются из оценки.

Ещё ожидается реальное первое завершение матча после подключения сборщика. До этого проверены процесс, локальное TCP-соединение и тесты обработки событий; живой полный проход server→GitHub→сайт не выдаётся за подтверждённый матч.
